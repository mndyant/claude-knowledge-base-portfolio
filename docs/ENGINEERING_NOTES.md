# 設計と改善の要点

## 入力上限を実測する

旧処理では平均1,101トークンのチャンクを512トークン上限のモデルへ渡していました。例外が出なくても後半が切り捨てられるため、処理の完了だけでは検索品質を保証できません。

構造保持分割はe5の実トークナイザーを使い、target=400 / max=480 / overlap=50を基本にします。入力prefixとspecial tokensも512に含まれます。トークナイザーを読み込めない場合は失敗として扱います。

## 文書の構造と検索粒度

見出し・コードフェンス・表・リストのまとまりを保持します。巨大なコードはフェンスを維持して分割し、見出し文脈を付けます。小チャンク化は順位を改善した一方、登録件数と処理コストが増えました。評価の母集団と条件をそろえて比較します。

SDKの同じ列挙定数が繰り返されて検索を支配する問題には、表示用本文を残し、埋め込み用テキストだけから反復部分を間引く対策を行いました。

## 中断と差分更新

構造保持経路のチャンクIDは内容を基準とします。位置が変わっただけの内容を再登録せず、upsert・処理済みID確認で再開します。削除された内容は対象prefix内でpruneします。従来Markdown経路のIDとは扱いを分けます。

`shard_split.py` はパートごとの分割を再開でき、`reembed.py --max-seconds 200` は埋め込み処理を区切れます。`--reset` はコレクションの削除が必要な場合だけ使います。通常の再開には不要です。

## 出典とタイトルの対応

生成モデルの結果を番号付き辞書で受け取ると、0始まりの添字と1始まりの引用番号が混同される場合がありました。配列と位置対応を使い、複数出典の回帰テストで対応を検証しています。

## 検証の分離

- pytestはモデルをテストダブルに置き換え、HTTPをモックし、DBを分離します。
- サンプルデモは自作文書4件と実e5モデルを使い、外部LLMなしで検索します。
- 過去の検索・回答品質評価は `EVAL.md` に記録します。全量コーパスの再測定とは区別します。
- 実API接続・実通知は別の確認事項です。
